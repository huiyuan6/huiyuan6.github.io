## 0. 需求来源（用户原始需求，逐字保留）

> "帮我开发一个会员权益官网，按 Spec-Driven Development 流程完成需求规格、技术设计、任务拆解、编码实现、单元测试、代码审查与功能验证，一站式交付。data.js中一个链接一个官网，通过底部友情链接互相跳转，都添加几个友链：券宝 https://jdjdndn.github.io/ 、聚合优惠 https://wcbblll.cc 、号卡 https://dlhaoka.com；页面元素不要太少；部署到github page；本地也要能正常访问；seo和ai友好；不要像新手站长做出的东西"

**解读要点确认**（与任务派发方共识，如与原始需求有出入以原始需求为准）：

1. 本站为会员权益聚合导航官网，是站群成员之一；data.js 中一个链接代表站群中的一个官网，站点之间通过各自底部"友情链接"区块互相跳转。
2. 本站底部友情链接必须包含 6 个站点：data.js 原有 3 站（运来网络、好运权益、福来流量站）+ 用户指定 3 站（券宝、聚合优惠、号卡）。
3. "页面元素不要太少"解读为：首页必须是内容丰富的单页（或少量页面），包含验收级别的完整板块清单（见 FR-04 ~ FR-13）。
4. "本地也要能正常访问"解读为：直接双击 index.html（file:// 协议）与任意静态 HTTP 服务器均可完整使用。
5. "不要像新手站长做出的东西"解读为：需具备设计系统、响应式、暗色模式、微交互、无障碍、性能等专业质感（见第 5 章非功能需求）。

## 1. 项目背景与目标

### 1.1 背景

会员权益类站点（视频/音乐/网盘会员、流量话费、社交媒体服务等）通常以站群形式运营：每个站点是一个独立官网，站点之间通过底部友情链接互相导流。本站（huiyuan6.github.io）是该站群中的会员权益聚合导航官网，负责：

- 向访客展示会员权益的分类与合作站点入口，完成导流；
- 通过底部友情链接与站群其他成员站点互相跳转；
- 仓库中已有 data.js（裸数组字面量）定义站群站点清单，需改造为可被页面消费的数据源。

### 1.2 项目目标

1. 交付一个内容丰富、专业质感的会员权益聚合导航官网（单页为主）。
2. 建立 data.js 数据驱动的合作站点展示机制，并完成底部 6 站友链互跳。
3. 站点对搜索引擎与 AI 爬虫友好，可被正确理解、收录与引用。
4. 部署至 GitHub Pages，同时保证 file:// 本地直开与静态服务器访问均完整可用。
5. 按 SDD 流程一站式交付：spec → design → tasks → 编码 → 单元测试 → 代码审查 → 功能验证。

### 1.3 范围

**范围内**：

- 站点前端静态页面（HTML/CSS/JS）及配套静态资源；
- data.js 数据改造与消费；
- SEO / AI 友好相关静态文件（robots.txt、sitemap.xml、llms.txt 等）；
- GitHub Pages 部署与本地访问验证；
- 单元测试、代码审查、功能验证等质量活动。

**范围外**：

- 不开发任何后端服务、数据库、用户系统、订单支付；
- 不修改站群其他成员站点（友链对端）的任何内容；
- 不建设 CI/CD 流水线（GitHub Pages 用户仓库推送即部署）；
- 不做多语言站点（仅简体中文）。

## 2. 术语表

**会员权益**
: 视频平台会员、音乐平台会员、网盘/存储扩容、流量话费优惠、社交媒体服务（粉丝/关注/点赞/阅读）等数字权益商品与服务的统称。

**站群 / 合作站点**
: 由同一运营方维护、互相通过友情链接导流的一组独立官网。在本项目中指 data.js 中收录的各站点（运来网络、好运权益、福来流量站等），本站是其中一员。

**友情链接（友链）**
: 页脚中指向站群内其他站点（或指定伙伴站点）的超链接区块，是站群互相跳转的载体。

**data.js**
: 仓库根目录的站点清单数据文件。语义：数组中一个条目代表站群中的一个官网。现状为裸数组字面量，需改造为暴露全局变量的脚本（见第 6 章）。

**全局数据变量（MEMBER_SITE_DATA）**
: data.js 加载后向页面暴露的全局变量名，页面脚本通过它读取站点清单。命名可在设计阶段调整，但必须唯一、稳定。

**数据驱动板块**
: 页面中内容由 data.js 数据渲染生成（而非硬编码在 HTML 中）的板块，如合作站点展示区。

**Hero 区**
: 首屏主视觉区块，包含主标题、价值主张与行动号召按钮。

**FAQ 手风琴**
: 常见问题板块的交互形式：默认只显示问题列表，点击/键盘激活后展开对应答案，同一时刻仅展开一项。

**JSON-LD**
: 内嵌于页面的结构化数据格式（schema.org 词汇），用于向搜索引擎与 AI 系统描述站点实体（WebSite、Organization、ItemList、FAQPage）。

**llms.txt**
: 部署在站点根目录、面向大模型/AI 爬虫的纯文本站点概览文件。

**file:// 本地访问**
: 不启动任何服务器、直接用浏览器打开本地 index.html 的访问方式。此方式下 fetch/XHR 受 CORS 限制，因此数据文件必须以 `<script src>` 标签方式加载。

**SDD（Spec-Driven Development）**
: 以规格文档驱动的一站式开发流程：需求规格 → 技术设计 → 任务拆解 → 编码实现 → 单元测试 → 代码审查 → 功能验证。

## 3. 用户角色

### 3.1 人类角色

- **访客（普通用户）**：通过搜索引擎、社交分享或站群其他站点友链进入本站，浏览权益分类与合作站点，点击入口跳转到目标站点完成权益开通。使用手机、平板或桌面浏览器。
- **站群站长（数据维护者）**：站群运营人员，通过编辑 data.js 增删站点条目来维护合作站点清单，期望改数据即可生效、不需要修改页面代码。

### 3.2 外部系统 / 非人类角色

- **搜索引擎爬虫**：抓取并收录本站，依赖语义化 HTML、meta、结构化数据、robots.txt 与 sitemap.xml。
- **AI 爬虫 / AI 助手**：读取本站内容用于检索问答与推荐，依赖 llms.txt、结构化数据与无需执行 JavaScript 即可获取的核心内容。
- **GitHub Pages 服务**：托管并发布本站静态资源，正式地址 https://huiyuan6.github.io/。
- **站群其他成员站点**：通过各自页脚友链与本站互相跳转的对端站点。

## 4. 功能需求（EARS 格式）

> 句式约定：触发关键词（When / While / If / Where / The system shall）保留英文，条件与响应内容使用中文。每条需求附验收要点。

### 4.1 全局框架与导航

**FR-01 顶部导航栏**
: When 访客进入本站页面，the system shall 在页面顶部展示导航栏，导航栏包含品牌标识"会员权益"、站内主要板块的锚点链接（至少覆盖：权益分类、合作站点、热门权益、常见问题）以及明暗主题切换控件。
- 验收要点：导航栏各锚点与页面实际板块一一对应；品牌标识可点击回到页面顶部。

**FR-02 锚点导航与焦点管理**
: When 访客点击导航栏或页内的板块锚点链接，the system shall 平滑滚动至目标板块，并将键盘焦点移至该板块（或等效的可聚焦目标）。
- 验收要点：每个锚点均可到达对应板块；目标板块获得焦点（可被辅助技术感知）。

**FR-03 暗色模式切换、记忆与系统跟随**
: When 访客点击主题切换控件，the system shall 立即切换整站明暗主题且无需刷新页面；While 访客再次访问本站，the system shall 恢复其上次手动选择的主题；While 访客从未手动选择主题且其操作系统处于深色模式，the system shall 默认呈现暗色主题。
- 验收要点：切换即时生效；刷新与重新访问后主题保持；未选择时跟随系统偏好。

### 4.2 首页内容板块（内容丰富性要求）

**FR-04 Hero 主视觉区**
: When 访客进入本站首页，the system shall 在首屏呈现 Hero 主视觉区，包含主标题（体现会员权益聚合定位）、副标题（一句话价值主张）、至少一个行动号召按钮（指向权益分类或合作站点板块）以及与品牌调性匹配的视觉元素。
- 验收要点：首屏不滚动即可完整看到主标题与行动号召按钮；按钮可点击并跳转到目标板块。

**FR-05 数据统计区**
: The system shall 在首页展示数据统计区，以醒目数字呈现站点核心数据（如权益分类数量、收录合作站点数量、覆盖权益场景数量）；其中合作站点数量必须与 data.js 有效条目数一致。
- 验收要点：统计数字与页面实际内容一致；合作站点数随 data.js 条目数联动。

**FR-06 权益分类卡片**
: The system shall 在首页展示权益分类板块，以卡片形式呈现至少 4 类权益（必须覆盖：视频会员、音乐会员、网盘/存储、社交媒体服务或流量话费），每张卡片包含分类图标、分类名称、权益说明及引导入口。
- 验收要点：分类数量 ≥ 4；每张卡片图标、名称、说明、入口四要素齐全。

**FR-07 合作站点展示（数据驱动）**
: While data.js 成功加载且包含至少一条有效站点记录，the system shall 在首页合作站点板块按数据顺序渲染站点卡片，每张卡片展示站点名称、一句话描述与访问入口，点击访问入口在新标签页打开对应 URL。
- 验收要点：渲染条目数、顺序、名称、描述与 data.js 一致；链接 target="_blank" 且带 rel 安全属性。

**FR-08 使用步骤指引**
: The system shall 在首页展示使用步骤板块，以分步形式（至少 3 步）说明访客如何通过本站获取会员权益（如：选择权益分类 → 查看合作站点 → 前往站点开通）。
- 验收要点：步骤数量 ≥ 3；步骤顺序符合实际使用路径。

**FR-09 热门权益/套餐展示**
: The system shall 在首页展示热门权益/套餐板块，以卡片或列表形式呈现推荐权益组合（如"追剧套餐""听歌套餐"等），每个条目包含名称、适用场景说明与权益亮点。
- 验收要点：推荐条目数量 ≥ 3；每个条目三要素齐全。

**FR-10 FAQ 手风琴**
: The system shall 在首页展示常见问题（FAQ）板块，以手风琴形式呈现至少 5 个问答对；When 访客点击或通过键盘（Enter/Space）激活任一问题，the system shall 展开该问题的答案并收起其他已展开项。
- 验收要点：问答对数量 ≥ 5；同一时刻最多展开一项；键盘可完成全部操作。

**FR-11 信任背书与用户评价**
: The system shall 在首页展示信任背书/用户评价板块，包含至少 3 条用户评价或信任要素（如服务保障说明、站点收录标准、用户反馈）。
- 验收要点：评价/背书条目数量 ≥ 3，呈现形式专业可信。

**FR-12 底部友情链接区（站群互跳）**
: Where 本站作为站群成员站点，the system shall 在页脚展示友情链接区块，完整包含以下 6 个站点入口，每个友链以站点名称为锚文本、在新标签页打开：
  1. 运来网络 — https://wcbblll.99kami.com （data.js 原有）
  2. 好运权益 — https://wcbblll.im01.cn （data.js 原有）
  3. 福来流量站 — http://35568.qcxmt.cn （data.js 原有）
  4. 券宝 — https://jdjdndn.github.io/ （用户指定）
  5. 聚合优惠 — https://wcbblll.cc （用户指定）
  6. 号卡 — https://dlhaoka.com （用户指定）
- 验收要点：6 个友链一项不缺、URL 逐字符准确、锚文本为站点名称；友链可被不执行 JavaScript 的爬虫获取（见 NFR-07）。

**FR-13 页脚站点信息**
: The system shall 在页脚展示站点基本信息（站点名称、版权声明与年份）及回到顶部入口。
- 验收要点：版权年份正确；回到顶部入口可用。

### 4.3 数据层（data.js）

**FR-14 data.js 脚本化加载与全局变量暴露**
: When 页面通过 `<script src="data.js">` 标签加载 data.js，the system shall 将站点清单数组暴露为全局变量（如 `MEMBER_SITE_DATA`），供页面脚本读取；data.js must 保持为无需任何构建步骤即可直接加载的纯 JavaScript 文件。
- 验收要点：浏览器控制台可直接访问该全局变量；双击打开 index.html（file://）时数据加载成功。

**FR-15 数据驱动的渲染联动**
: If 站点维护者在 data.js 中增加、删除或修改站点条目，the system shall 在页面重新加载后使合作站点板块的展示随之变化，而无需修改任何 HTML/JS 代码。
- 验收要点：对 data.js 做增删改后刷新页面，合作站点板块自动同步。

**FR-16 条目结构兼容与扩展**
: While data.js 中存在本规格未定义的扩展字段（如 tag、category、icon），the system shall 正常渲染 name/url/desc 基础字段并忽略无法识别的扩展字段，不得抛出错误。
- 验收要点：数据中加入任意扩展字段不影响页面渲染与控制台无错。

**FR-17 数据异常容错**
: If data.js 中某条目缺失必填字段（name/url/desc）或 url 不是合法的 http/https 绝对地址，the system shall 跳过该无效条目或降级展示，并在浏览器控制台输出可定位的警告信息；the system shall 保证任一无效条目不导致整页渲染失败。
- 验收要点：构造含无效条目的 data.js 后页面仍正常呈现其余内容；控制台有警告。

### 4.4 微交互与动效

**FR-18 悬停/聚焦反馈**
: When 访客将鼠标悬停或通过键盘聚焦于可交互元素（导航链接、按钮、卡片、友链），the system shall 提供可感知的视觉反馈（如高亮、阴影、位移或强调色变化）。
- 验收要点：全部可交互元素均有 hover 与 focus 两态反馈。

**FR-19 滚动入场动效与减少动态偏好**
: When 内容板块随页面滚动进入可视区域，the system shall 以渐显、上移等温和方式呈现入场动效；While 访客的系统开启了"减少动态效果"（prefers-reduced-motion）偏好，the system shall 禁用入场动效并直接呈现内容。
- 验收要点：正常环境有入场动效；开启减少动态偏好后无动效且内容完整可见。

## 5. 非功能需求（NFR）

### 5.1 SEO 友好

**NFR-01 语义化 HTML 与标题层级**
: The system shall 使用语义化 HTML5 元素组织页面结构（header/nav/main/section/article/footer），标题层级自 h1 起逐级递减，且每个页面仅包含一个 h1。
- 验收要点：HTML 校验无结构性错误；heading 层级无跳级。

**NFR-02 基础元数据完整性**
: The system shall 为页面提供完整 head 元数据：包含品牌关键词的唯一 title、准确概括页面内容的 description、keywords、以及指向正式地址 https://huiyuan6.github.io/ 的 canonical 链接。
- 验收要点：四类 meta 齐全；canonical 指向正式域名。

**NFR-03 社交分享卡片**
: The system shall 提供 Open Graph（og:title、og:description、og:type、og:url、og:image）与 Twitter Card（twitter:card 等）元数据，确保页面被分享至社交平台时呈现结构化摘要卡片。
- 验收要点：OG/Twitter 标签齐全且 og:image 可访问。

**NFR-04 JSON-LD 结构化数据**
: The system shall 在页面内嵌 JSON-LD 结构化数据，覆盖四类实体：WebSite（站点信息）、Organization（运营主体）、ItemList（合作站点清单）、FAQPage（与页面 FAQ 内容一致的问答），且结构化数据内容与页面可见内容保持一致。
- 验收要点：四类实体齐全；JSON-LD 语法可通过标准校验工具；内容与页面一致。

**NFR-05 爬虫辅助文件**
: The system shall 在站点根目录提供 robots.txt（允许全部抓取并声明 sitemap 地址）与 sitemap.xml（包含首页规范 URL）。
- 验收要点：两个文件在正式地址下可访问（https://huiyuan6.github.io/robots.txt、/sitemap.xml）。

### 5.2 AI 友好

**NFR-06 llms.txt**
: The system shall 在站点根目录提供 llms.txt 文件，以纯文本概览站点定位、核心板块、合作站点清单与入口，供 AI 爬虫与 AI 助手理解与引用本站。
- 验收要点：https://huiyuan6.github.io/llms.txt 可访问，内容准确覆盖站点结构。

**NFR-07 无 JavaScript 核心内容可用**
: If 浏览器禁用 JavaScript 或脚本加载失败，the system shall 仍可获取核心内容：页面全部板块标题与文本内容、权益分类、FAQ 问答文本、以及全部 6 个友情链接（具体实现方式由设计阶段决策）。
- 验收要点：以禁用 JS 方式（或纯 HTTP GET）访问页面可获取上述内容。

### 5.3 性能

**NFR-08 无框架依赖与轻量化**
: The system shall 以原生 HTML/CSS/JavaScript 实现，不依赖任何前端框架、构建链或第三方运行时库；页面核心资源（HTML + CSS + JS，不含图片与字体）总体积不超过 200 KB。
- 验收要点：仓库无框架依赖；核心资源体积达标。

**NFR-09 首屏加载性能**
: The system shall 在常规网络环境下于 2 秒内完成首屏内容呈现与可交互（本地与 GitHub Pages 环境均需满足）；非首屏图片资源应采用懒加载。
- 验收要点：本地与线上首屏可交互时间 ≤ 2s；非首屏图片带懒加载属性。

### 5.4 可访问性

**NFR-10 键盘可达性**
: The system shall 保证全部交互元素（导航、按钮、FAQ 手风琴、友链、主题切换）可通过键盘 Tab / Enter / Space 完整操作，焦点顺序与视觉顺序一致且焦点状态可见。
- 验收要点：仅用键盘可完成"切换主题 → 导航到 FAQ → 展开问答 → 点击友链"全流程。

**NFR-11 文本对比度**
: The system shall 保证明、暗两种主题下正文文本对比度不低于 WCAG 2.1 AA 级（普通文本 ≥ 4.5:1，大字号文本 ≥ 3:1）。
- 验收要点：两主题下主要文本区域对比度抽检达标。

**NFR-12 图片替代文本与 ARIA**
: The system shall 为所有非装饰性图片提供有意义的 alt 文本，为图标按钮、手风琴等控件提供恰当的 aria 属性，纯装饰性图形标记为对辅助技术隐藏。
- 验收要点：无非装饰性图片缺 alt；手风琴与图标按钮 aria 正确。

### 5.5 响应式

**NFR-13 移动端优先响应式**
: The system shall 采用移动端优先的响应式布局，在 320px 至 1920px 及以上视口宽度下均无横向滚动条、无元素重叠、无内容截断，断点至少覆盖手机、平板、桌面三类设备形态。
- 验收要点：320px / 768px / 1024px / 1440px 视口抽检布局正常；移动端导航可用（如汉堡菜单）。

### 5.6 本地可访问性

**NFR-14 file:// 协议完整可用**
: The system shall 支持在本地文件系统直接双击 index.html 打开（file:// 协议）并完整使用全部功能（data.js 数据加载、板块渲染、导航、主题切换与记忆、FAQ 手风琴、友链跳转），不因浏览器 CORS 策略失败；the system shall 同时兼容任意静态 HTTP 服务器访问。
- 验收要点：file:// 下全部功能验证通过；本地静态服务器（任意端口）下验证通过。

### 5.7 部署与交付

**NFR-15 GitHub Pages 部署**
: The system shall 以纯静态站点形式部署于 GitHub Pages 用户仓库（huiyuan6.github.io）：全部站点资源位于仓库默认分支根目录，推送后自动发布，正式地址为 https://huiyuan6.github.io/，不依赖任何 CI 配置。
- 验收要点：推送默认分支后线上地址可访问且功能完整；资源引用路径在根路径部署下正确。

**NFR-16 SDD 一站式交付流程**
: 本项目 shall 按 Spec-Driven Development 流程完成并归档全部阶段产出物：需求规格（spec.md）→ 技术设计（design.md）→ 任务拆解（tasks.md）→ 编码实现 → 单元测试 → 代码审查 → 功能验证，用户中途无需确认（一站式交付）。
- 验收要点：各阶段产出物存在于仓库约定目录；测试、审查、验证结论可追溯。

## 6. 数据需求

### 6.1 data.js 现状与改造约束

**现状**：仓库根目录 data.js 为裸数组字面量（未赋值给任何变量），内容包含 3 个站点条目：

```js
[
  { name: '运来网络', url: 'https://wcbblll.99kami.com', desc: '视频/音乐/网盘等权益' },
  { name: '好运权益', url: 'https://wcbblll.im01.cn', desc: '视频/音乐/网盘等权益' },
  { name: '福来流量站', url: 'http://35568.qcxmt.cn', desc: '粉丝/关注/点赞/阅读服务' },
]
```

**改造硬约束（兼容性要求）**：

1. data.js must 改造为可被 `<script src="data.js">` 标签直接加载的脚本，加载后将站点清单数组暴露为全局变量（实现方式如 `const MEMBER_SITE_DATA = [...]` 或等价的 window 级赋值，具体命名由设计阶段确定并在 design.md 中固化）。
2. 数据条目结构（name / url / desc 三字段）must 保持兼容：现有 3 条数据的字段名与取值不发生变化（逐字符保持）。
3. 数据结构 must 可扩展：支持追加新条目与新增可选字段，且不需要修改页面代码即可被数据驱动板块消费（见 FR-15 / FR-16）。
4. 改造后的 data.js 不得引入任何外部依赖、不得需要构建步骤。

### 6.2 数据条目字段约束

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| name | 是 | 非空字符串；站点显示名称，同时用作友链锚文本 |
| url | 是 | 合法的 http/https 绝对 URL；站点正式访问地址 |
| desc | 是 | 非空字符串；一句话站点描述，建议不超过 30 个汉字以保证卡片排版 |
| （扩展字段） | 否 | 如 tag / category / icon 等；缺失时不得影响基础渲染（见 FR-16） |

## 8. 设计阶段需重点决策的问题

以下问题不改变本规格的验收结果，但需要在 design.md 中给出明确决策：

**D1. 数据驱动渲染与无 JS 可用性的实现路径**
FR-07/FR-15 要求合作站点由 data.js 数据驱动渲染，NFR-07 要求禁用 JavaScript 时 6 个友链与核心内容仍可获取。需决策：采用构建期内联数据、双写静态降级（noscript）、还是首屏静态 + 增强渲染等方案，并明确对维护成本的影响。

**D2. 用户指定 3 个友链（券宝/聚合优惠/号卡）的数据管理方式**
三个新增友链是并入 data.js 统一管理（合作站点板块与页脚共用同一数据源），还是作为独立的友链配置与 data.js 分离（合作站点仅展示站群成员）。两种方式均满足 FR-12，需权衡语义清晰度与维护成本。

**D3. 设计系统的视觉方向**
品牌主色与明暗双主题配色体系、中文字体方案（系统字体栈 vs 引入 web 字体，需权衡 NFR-08/NFR-09 性能预算）、视觉基调（如何体现"不像新手站长"的专业质感），需产出可执行的设计令牌规范。

**D4. 暗色模式的技术策略与一致性**
主题的记忆与恢复在 file:// 与 GitHub Pages 两种环境下需行为一致，需确定存储机制与首帧闪烁（FOUC）的规避方案。

**D5. 单元测试的可测性设计**
纯静态站点需要明确测试切入点：数据校验逻辑、渲染函数、交互行为应如何模块化组织，以及测试工具与运行方式（如 Node 原生 test runner / 无头浏览器方案）的选择。
